# Known limitations

- Disable flags (`cmd statusbar send-disable-flag`) are volatile and reset on reboot / SystemUI restart. The `BOOT_COMPLETED` receiver handles this automatically, but **Shizuku must be configured to start on boot**.
- Disable flags are also a **shared, last-writer-wins slot**: AOSP's `StatusBarShellCommand` registers every `cmd statusbar send-disable-flag` caller under one static token (`pkg=android` in `dumpsys statusbar`), so each invocation *replaces* the record instead of OR-ing into it -- any other app running its own `send-disable-flag ...` silently wipes ours. Observed on the test device: **Essentials** (`com.sameerasw.essentials`) re-ran `send-disable-flag clock notification-icons` through Shizuku around every unlock, dropping our `system-icons` bit (`mDisabled1 0x920000 -> 0x820000`) and bringing the whole system status bar back while the app still reported *Hidden*. Attribution was pinned with `dumpsys statusbar` (`mDisableRecords`), an `atrace` binder trace (the offender's `SHELL_COMMAND_TRANSACTION` lands ~60 ms before the wipe) and an A/B/A run (Essentials running -> wipe on every unlock, force-stopped -> no wipe over a full cycle, relaunched -> wipe returns). **Turning its status-bar options off does not stop it**: with the *Statusbar icons* module entirely off (master switch and every toggle) the wipe still fires on every unlock, now as a total clear (`0x920000 -> 0x0`) instead of the partial one. **The culprit is no UI feature at all**: `EssentialsApp.onCreate()` registers a `SecurityReceiver` for `SCREEN_OFF`/`SCREEN_ON`/`USER_PRESENT` unconditionally, and every `ACTION_USER_PRESENT` makes it call `StatusBarManager.reassertFlags()`, which re-applies with `force = true` -- bypassing both "nothing to do" guards in `applyLocked` -- and, since Essentials has no flags of its own left (exported config: `island_enabled`, `duo_enabled`, `status_bar_icon_control_enabled`, `maps_power_saving_enabled`, `hide_clock`, `hide_notification_icons` all false and `saved_automations` empty), always emits a bare `send-disable-flag none`. That is why toggling anything in its *Display* or *Statusbar icons* screens changes nothing. The whole chain shows up in one `atrace --async_start sched binder_driver` run: an Essentials thread calls `IShizukuService` on `shizuku_server` ~1 ms before it forks `sh -c ...`, the resulting `cmd` sends `SHELL_COMMAND_TRANSACTION` (`_CMD`, code `0x5f434d44`) to the statusbar service ~35 ms later, and our record's `what1` goes to `0x00000000` on the very token we own (`StatusBarShellCommandToken`, `pkg=android`). Timing, measured with a 30 ms `dumpsys statusbar` poll against the ms-precision `dispatchClockTime` of `dumpsys activity broadcasts`: the wipe lands ~610 ms after `ACTION_USER_PRESENT` is dispatched and ~110 ms after that broadcast finishes -- it is driven *by* the unlock broadcast, not before it -- and our own re-apply heals it ~300 ms later. Neither of the two obvious blockers works: a full `global`/`secure`/`system` `settings` diff taken around the wipe is empty (it is not a settings write), and revoking Essentials' Shizuku permission does not cut it off: `Shizuku.checkSelfPermission()` short-circuits on its cached `permissionGranted` boolean whenever that flag is already `true`, and the flag is only rewritten when the Shizuku binder is (re)received -- so a running Essentials process keeps its cached *granted* answer until Essentials or Shizuku restarts. When tracing this yourself, beware that `0x5f504e47` is `_PNG_` -- the ping sent while looking a service up, emitted by every `dumpsys`/`cmd` -- and not the shell command, which is `_CMD`. The app therefore does not trust the slot: `HideInteractor` remembers the bits its own apply read back, and the unlock watch re-checks at 300/700/1500/3000 ms, so a wipe is detected and re-applied at the first 300 ms check on the measured unlocks (3 s worst case). To diagnose by hand, `dumpsys statusbar | grep -E "mDisabled1|what1="` shows our record's `what1` at `0x00000000` while the other writer is in force.
- OEM background restrictions (MIUI autostart, Samsung sleeping apps, OnePlus auto-launch, ...) are private AppOps with **no read API**: the setup checklist's *Keep alive* rows can only open the right settings screen, never report whether the toggle is set. The one state that *is* readable -- the Doze battery optimization exemption -- is shown with a real granted / missing mark.
- `ShellRunner` calls `IShizukuService.newProcess()` directly via the `aidl` artifact instead of the deprecated `Shizuku.newProcess()` method (private since Shizuku 13.1.5). Stdout and stderr are drained concurrently with a timeout to avoid pipe deadlocks, and the **exit code is honoured** (a failing command is reported as `FAILED`, not silently swallowed).
- The overlay uses `FLAG_SHOW_WHEN_LOCKED` to draw above the keyguard; without the toggle it behaves like a normal overlay window. "Clock only" is strict: the clock widget is the only thing drawn while locked.
- The custom bar is a `TYPE_APPLICATION_OVERLAY` window, and since Android 11 overlays are blocked over the **Settings app** (an anti-tapjacking guard; Google tracks it as *intended behaviour* in issue 161156067), so the bar does not draw there. The official escape hatch is **Developer options > Allow screen overlays on Settings** (secure key `secure_overlay_settings`), but enabling it does not reliably take effect either -- the bar can still stay hidden inside Settings. A missing bar on system settings screens is therefore expected, not a bug.
- The app blacklist needs **usage access** (Settings > Apps > Special access > Usage access) and polls the foreground package every 2 s while the feature is on; without the grant the feature stays inert and says so in the log.
- The SystemUI watcher polls the SystemUI PID (no system callback exists for it), so a restart can take up to **60 s** to be noticed, and the hide commands are re-applied only while the app is running (the `BOOT_COMPLETED` receiver covers reboots).
- Backup files carry a `schema_version`; a backup written by a newer build is refused instead of being half-applied. An import larger than 64 KiB is refused while reading, so a hostile file is never buffered whole.
- The lock-screen overlay runs through an accessibility service. Enabling it writes into `enabled_accessibility_services` (merging with whatever is already there), and it stays on like any other accessibility service until *Disable lock-screen overlay (accessibility)* is pressed.
- The camera ring (including the Style-tab preview) can only be drawn around a **detected** cutout; devices without a punch-hole / notch get no ring geometry to place. The preview also requires the custom bar to be visible.
